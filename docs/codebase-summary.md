# RDK-RZ/V2H Codebase Summary

**Status:** Navigation for the checked-in RZ/V2H port

This page answers where a contributor should look. It does not duplicate the
driver inventory, evidence tiers, pin tables, or generated configuration.
Those facts belong to the executable owners and the linked status documents.

## 1. NuttX RZ/V2H Driver Port

The NuttX submodule owns the RZ/V2H architecture and lower-half drivers:

- `platforms/nuttx/NuttX/nuttx/arch/arm/src/rzv/` — startup, clocks, MPU,
  interrupt routing, GPIO/pin control, serial, SPI/I2C, timers/PWM, DMA,
  storage, ADC, CAN-FD, watchdog, Ethernet, and IPC implementations.
- `platforms/nuttx/NuttX/nuttx/boards/arm/rzv/rdk-rzv2h/` — board startup,
  linker scripts, board glue, and NuttX configuration directories.
- `platforms/nuttx/NuttX/apps/` — NuttX applications used by the selected
  configurations.

Use the [NuttX port status](./renesas/port-status-nuttx.md) for per-driver
ownership and evidence. The source tree and each configuration's `defconfig`
remain authoritative for enabled symbols and implementation details.

## 2. NuttX Board Configurations

The board root is
`platforms/nuttx/NuttX/nuttx/boards/arm/rzv/rdk-rzv2h/`. Its `configs/`
profiles are selected through
`platforms/nuttx/NuttX/build.sh`; use `platforms/nuttx/NuttX/build.sh --list`
for the current set. `src/`, `include/`, and `scripts/` own board bring-up,
headers, memory views, and image construction.

NuttX-only builds are for driver bring-up, shell configurations, and bounded
peripheral or IPC experiments. They do not by themselves prove PX4 integration
or production readiness.

## 3. PX4 Board & Platform Layer

The PX4 board definitions live under `boards/renesas/rdk-rzv2h/` and the
standalone IO board roots `boards/renesas/rdk-rzv2h-io-cr8_1/` and
`boards/renesas/rdk-rzv2h-io-cm33/`. Board manifests, Kconfig fragments,
startup files, and board-local sources select the profile-specific behavior.

The RZ/V2H PX4 platform layer lives under
`platforms/nuttx/src/px4/renesas/rzv/`; its subdirectories own the HAL glue
for board setup, timers/HRT, GPIO/IO pins, reset, SPI, and related platform
interfaces. The [PX4 HAL status](./renesas/port-status-px4-hal.md) records
which interfaces have evidence at each tier.

The registered PX4 target set is generated by the build system. Discover it
with `./build.sh --list`; do not copy a target inventory into this document.
The retired core-only resources under the RDK board tree are historical and do
not represent an active target.

## 4. References (Source of Truth)

Local, gitignored reference material is under `refs/` when present:

- `refs/rzv2h_drone_px4-dev/` — selected RDK FreeRTOS/FSP reference used for
  source comparison and the opt-in drone extension.
- `refs/rzv2h_evk/` — per-core EVK FSP examples used for peripheral behavior;
  their EVK pin data is not an RDK pin contract.
- `refs/rzv2h_gb_ether/` — Ethernet reference.
- `refs/rzv2h_scripts/` — pinmap and generated-artifact tooling.

Evidence precedence and source selection are defined by
[reference-source-map.md](./renesas/reference-source-map.md). The RDK board
pin and wiring authority is [pinmap.md](./renesas/pinmap.md) together with the
board-owned pinout source.

## 7. Key Build Artifacts

The checked-in build scripts own artifact names and output layout:

- `./build.sh <target>` produces the selected PX4 build under `build/<target>/`.
- `platforms/nuttx/NuttX/build.sh <config>` produces the selected NuttX image
  under `platforms/nuttx/NuttX/nuttx/`.

Use the [deployment guide](./deployment-guide.md) for build, RAM-load, RTT,
and debug procedures. Do not infer a flashing or cold-boot route from the
presence of a binary artifact.

## 9. Discovery Tips

Start from the owning source or executable route:

1. Use `./build.sh --list` or `platforms/nuttx/NuttX/build.sh --list` to
   discover current targets and configurations.
2. Read the selected board manifest and `defconfig` before changing a profile.
3. Use the status tables and [validation route](./renesas/README.md) to find
   the evidence required for the relevant subsystem.
4. Use the [reference-source map](./renesas/reference-source-map.md) before
   comparing against FSP or EVK material.

The NuttX submodule and local `refs/` material are source dependencies, not
generated documentation. Preserve their ownership and do not hand-maintain a
file inventory here.
